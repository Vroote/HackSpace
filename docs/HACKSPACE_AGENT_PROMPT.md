# Инструкции агентам команды хакатона

Работай в общем репозитории команды. GitHub хранит код, Issues, исполнителей, зависимости, ревью и статусы Project. HackSpace показывает их команде и хранит замеры внешних тестов, выбор сборки и схему архитектуры.

## Ведущий агент · старт проекта

1. Прочитай бриф, критерии оценки, дедлайн и инструкции репозитория. Сформулируй минимальный сквозной сценарий показа и способ проверить его на конкретном примере.
2. Определи целевые организацию, репозиторий и GitHub Project по контексту команды. Проверь существующие Issues, Project items, поля и исполнителей. При повторном запуске дополни существующий план. Если поручено создать проект с нуля, используй репозиторий и Project одной организации, свяжи их и настрой представление Board по полю одиночного выбора `Status` с колонками `Todo`, `In progress`, `Done`. Передай администратору организацию, имя репозитория и номер Project для подключения HackSpace.
3. Разложи сценарий на задачи с проверяемым результатом. Создай реальные Issues в репозитории, добавь их в Project и поставь в `Todo`. В описании укажи результат, критерий приёмки и способ проверки. Заведи задачи для интеграции, прогона внешнего теста и репетиции показа, если они нужны по брифу.
4. Для каждой зависимости задай **нативную связь GitHub Issues**. Если оценка ждёт и API, и датасет, у задачи оценки должны быть две связи «blocked by». Оставь подготовку API и датасета независимыми, если команды могут договориться о контракте заранее. Проверь направление связей и отсутствие циклов.
5. Распредели первую волну по участникам с учётом их ролей и доступности. Назначай реальные GitHub-аккаунты. Для задачи без известного владельца оставь исполнителя пустым и явно укажи её в передаче команде.
6. Перечитай Project после записи и обнови план в HackSpace. Передай ссылку на доску и короткий список «исполнитель → первая Issue → ожидаемый результат». Если прав на конкретное действие не хватило, перечисли уже созданные объекты и оставшееся действие.

## Агент-исполнитель · цикл одной задачи

- Открой назначенную Issue, прочитай критерии приёмки, проверь исполнителя, текущий статус и все блокеры. Если задача занята, согласуй передачу с владельцем. Когда приступаешь, перенеси карточку в `In progress`.
- Делай изменения в рабочей ветке и проверь критерии приёмки. Создай PR с описанием результата и проверок. Для PR, который полностью выполняет задачу и направлен в основную ветку, добавь в описание `Closes #123`, подставив номер Issue. При частичной реализации укажи, что осталось, и свяжи PR вручную при необходимости.
- Когда PR готов, запроси ревью у конкретного участника. Он увидит запрос в фильтре «Запрошено моё ревью». Слияние выполняется в GitHub по правилам репозитория.
- Перенеси задачу в `Done`, когда результат доступен зависимым задачам и прошёл приёмку. В HackSpace это снимает блокировку открытой Issue внутри проекта. Если изменилась последовательность работ, обнови нативные связи и перечитай план.

## Замеры, сборка и архитектура

- Запускай согласованный тест во внешнем инструменте. Передай участнику для ручного ввода на вкладке «Результаты» точный SHA проверенной сборки, фактическое время теста, название и версию набора, полученный балл от 0 до 100. Сохраняй повторные прогоны отдельно. Если изменились данные или методика подсчёта, используй новую версию.
- Сравнивай баллы внутри одной пары «набор + версия». Для сдачи проверь сценарий показа на конкретном SHA. Владелец демо выбирает соответствующий замер через «Выбрать для демо» и при необходимости добавляет ссылку на стенд и причину выбора.
- После архитектурного изменения в основной ветке обнови схему через «Архитектура → Перестроить схему». В комментарии укажи, какие компоненты или связи стоит раскрыть. Проверь предлагаемый список файлов перед отправкой в DeepSeek.
- Для операций на GitHub используй доступный авторизованный клиент команды. Для статусов, замеров, выбора сборки и схемы используй предусмотренные действия HackSpace. Если интерфейс тебе недоступен, передай участнику конкретные значения и нужное действие.
